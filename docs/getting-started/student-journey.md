# Parcours étudiant officiel

Les quatre commandes publiques sont les seules que l’étudiant doit connaître. Codex orchestre les options internes, pose les questions une par une, ne choisit aucune valeur et ne demande la destination qu’après validation du brief et des choix techniques.

```text
Idée → validation → recherche et cahier des charges → choix techniques → dry-run → confirmation → génération → configuration → smoke auth → design facultatif → validation → rapport
```

| État stable                      | Rôle de l’agent et action suivante                                                                   | Fichiers requis                         | Action humaine                                                 | Interdictions et condition de sortie                                    |
| -------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `NEEDS_PROJECT_VALIDATION`       | Lire intégralement `Fanga_validation_projet.md`, commencer le bloc A.                                | workflow de validation                  | Répondre par blocs de 5 maximum.                               | Aucun code; sortir lorsque l’entretien initial est complet.             |
| `PROJECT_VALIDATION_IN_PROGRESS` | Reformuler, relever les contradictions et continuer un bloc à la fois.                               | notes de validation                     | Confirmer chaque synthèse.                                     | Aucun chiffre inventé; sortir lorsque les hypothèses sont explicites.   |
| `NEEDS_PRODUCT_RESEARCH`         | Rechercher avec sources datées et préparer la validation terrain.                                    | `RECHERCHE_MARCHE.md`, sources          | Autoriser les recherches ou fournir les preuves privées.       | Séparer faits, estimations et hypothèses.                               |
| `NEEDS_PROJECT_DECISION`         | Présenter une seule décision `GO_CONDITIONNEL`, `PIVOT` ou `NO_GO_TEMPORAIRE`.                       | analyse et score                        | Accepter la décision ou demander une révision.                 | `NO_GO_TEMPORAIRE` bloque le code; `PIVOT` reprend la validation.       |
| `NEEDS_TECHNICAL_ANSWERS`        | Après GO, poser uniquement la prochaine question technique non répondue.                             | documents produit, `FANGABASE_INPUT.md` | Choisir chaque valeur.                                         | Aucun défaut choisi; résoudre explicitement toute contradiction.        |
| `INVALID_ANSWERS`                | Expliquer l’erreur et ses conséquences.                                                              | réponses conservées                     | Corriger la réponse concernée.                                 | Aucune correction silencieuse.                                          |
| `READY_FOR_DRY_RUN`              | Valider le brief avec le schéma réel, demander une destination hors du dépôt et exécuter le dry-run. | brief, documents produit                | Donner la destination.                                         | Aucune génération.                                                      |
| `NEEDS_GENERATION_CONFIRMATION`  | Montrer tout le plan, les imports et UAT.                                                            | résultat du dry-run                     | Répondre exactement `OUI` ou `NON`.                            | Seul `OUI` autorise l’écriture.                                         |
| `GENERATING`                     | Générer atomiquement et vérifier le manifeste.                                                       | configuration validée                   | Aucune.                                                        | Ne jamais utiliser `--force` sans demande explicite.                    |
| `NEEDS_LOCAL_SETUP`              | Entrer dans le projet et exécuter `pnpm setup`.                                                      | projet généré                           | Installer un prérequis système réellement absent.              | Ne pas réinstaller inutilement.                                         |
| `NEEDS_ENV_CONFIGURATION`        | Créer `.env` depuis l’exemple et générer `APP_KEY` pour Laravel.                                     | `.env.example`                          | Renseigner localement les valeurs nécessaires.                 | Aucun secret dans la discussion ou Git.                                 |
| `NEEDS_EXTERNAL_CREDENTIALS`     | Identifier comptes, variables et UAT externes.                                                       | documentation service                   | Créer le compte/contrat et saisir le secret dans `.env`.       | Ne pas afficher le secret; le local facultatif ne doit pas être bloqué. |
| `READY_FOR_SMOKE`                | Exécuter doctor, migrations, tests, build et smoke auth local.                                       | commandes générées                      | Aucune sauf infrastructure externe.                            | Arrêter proprement les processus temporaires.                           |
| `NEEDS_DESIGN_ACTIVATION`        | Lire uniquement le workflow sélectionné.                                                             | `docs/design/`                          | Confirmer toute connexion/dépense/transmission externe.        | `headless` termine sans design.                                         |
| `DESIGN_IN_PROGRESS`             | Intégrer les références réelles écran par écran.                                                     | références choisies                     | Fournir maquettes ou effectuer l’action externe indispensable. | Aucun thème officiel, route inventée ou sécurité affaiblie.             |
| `READY_FOR_FINAL_VALIDATION`     | Relancer les gates fonctionnelles, visuelles si applicables, sécurité et secrets.                    | résultats de tests                      | Effectuer les UAT externes disponibles.                        | Une gate obligatoire rouge mène à `FAIL`.                               |
| `PASS`                           | Finaliser le rapport sans réserve obligatoire.                                                       | `docs/FANGABASE_FINAL_REPORT.md`        | Aucune.                                                        | Toutes les gates obligatoires et UAT requises sont vertes.              |
| `PASS_WITH_WARNINGS`             | Finaliser avec UAT externes clairement listées.                                                      | rapport final                           | Réaliser les UAT avant production.                             | Aucune gate locale obligatoire ne peut être rouge.                      |
| `FAIL`                           | Donner l’erreur exacte et la correction ciblée.                                                      | preuve de la gate                       | Décision seulement si action externe indispensable.            | Ne jamais masquer ni affaiblir un test.                                 |

Après `GO_CONDITIONNEL`, le dossier produit contient `PRD.md`, `CAHIER_DES_CHARGES.md`, `RECHERCHE_MARCHE.md`, `MVP.md`, `PARCOURS_UTILISATEURS.md`, `BACKLOG_MVP.md`, `RISQUES_ET_HYPOTHESES.md` et `FANGABASE_INPUT.md`. Ce dernier contient exactement un bloc `yaml fangabase` validé par le schéma. Les documents orientent le futur métier mais ne le génèrent jamais implicitement.
